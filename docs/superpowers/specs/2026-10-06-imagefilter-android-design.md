## 0. 30 秒速览

| 维度 | 事实 |
|---|---|
| 是什么 | 桌面端 ImageFilter 的**远程筛片客户端**。图库就是跑 ImageFilter 的那台电脑，手机通过 HTTP API 浏览并筛选 |
| 同步怎么发生 | 手机打分 → 服务端**由桌面端自己写 `.xmp`** → 桌面端本来就会读边车（`useScanner.ts:1020`）。**手机端不碰边车格式** |
| 形态 | 桌面端内嵌一个 axum 服务（新）；安卓侧原生 Kotlin + Compose 瘦客户端（**无 Rust、无 NDK、无 UniFFI**） |
| 网络层 | **L0** 只认"URL + token"（局域网零配置可用）；**L1** 连接向导内置打通引导并自动探测本机已装的组网工具；**不做任何中继/穿透服务** |
| 引导首选 | **EasyTier**（无需账号、无需公网 IP、有公共共享节点、有安卓 APK）→ 备选 Tailscale / Cloudflare Tunnel |
| 手机端不做 | AI 分析、导入归档、删除文件、RAW 解码、边车读写、任何 Rust |
| 离线 | 只看 Coil 已缓存的图；改动失败 → 本地待重试队列（很小，不是冲突合并） |
| 安全 | 服务默认关闭；强制 Bearer token；**共享根白名单**（路径必须落在显式共享的目录内）；不做 TLS，靠网络边界（局域网或加密隧道） |
| 性能 | 缩略图/预览由**服务端**生成与降采样；手机侧 Coil 负责缓存、硬件位图、滚动取消 |
| 验证 | Rust 单测 + 服务端契约脚本（PS 5.1）+ Kotlin JVM 单测 + 真机手测（性能只认真机） |

## 1. 目标与非目标

### 1.1 目标

1. 人在外面时，用手机浏览电脑上的照片（JPEG + RAW 都行，**由电脑解码**），完成初筛。
2. 初筛结果（星级 0–5、五色标签）落到 `.xmp` 边车，桌面端随后自动合并，接着走原有导入归档链。
3. 支持把入选片**移动到子文件夹**（如 `精修/`），在手机上完成一次粗分类。
4. 已看过的内容离线可看（Coil 磁盘缓存）。
5. **别人下载下来也能用**：不假设使用者有 NAS、有公网 IP、有 IPv6、会配置路由器。同一 WiFi 下开箱可用；跨网只需装一个组网工具（向导里带路）。

### 1.2 非目标（已逐条确认）

| 不做 | 理由 |
|---|---|
| 手机端 AI 分析 | 用户明确排除。**注意**：`analyze_photos` / `find_duplicates` 的结果在桌面端只存内存、不落盘（`analyzer.rs` 的 `AnalysisResult` 未持久化），所以手机也读不到；要做得先把结果落 SQLite，另开一轮 |
| 导入归档 / MD5 校验 | 留在电脑上；`importer.rs` 的"绝不静默覆盖 + 双端 MD5"契约不在手机上重造 |
| 删除远端文件 | 不可逆，且会与 `import_history` 失去对账 |
| **自建中继 / 穿透 / 打洞服务** | 要服务器、要持续流量费、要运维、要承担安全与滥用责任。连 Immich 都不做，Plex 的免费 relay 也已转付费（见附录 A #4） |
| 手机端 RAW 解码 / Rust / UniFFI / NDK | 解码在电脑上（四级链：内嵌 JPEG → WIC → rawler → tinydng），手机只拿 JPEG |
| 手机端读写 `.xmp` | 边车格式是桌面端 `xmp.rs` 的事，手机不该有第二份实现 |
| 勾选（`selectedPaths` 的等价物） | 桌面端勾选是纯内存态（`useScanner.ts:89`），无法跨端传递；手机端用**色标**表达取舍 |
| 视频 | 缩略图链与播放器会显著拉大体积 |
| iOS | 只要安卓。若将来要，Flutter 应重新评估（附录 A #6） |

### 1.3 硬前提（首启引导必须显式给出操作路径）

**电脑上必须正在运行 ImageFilter，且"图库服务"已开启。** 电脑睡眠、ImageFilter 未启动、服务未开、Windows 防火墙拦了入站——这四件事都会表现为"手机连不上"，而用户从手机这一侧看不出原因。首启引导必须把这四条列成排查清单。

## 2. 技术选型

### 2.1 结论

| 侧 | 技术 |
|---|---|
| 桌面端服务 | 进程内 **axum**（tokio 已是既有依赖）+ Bearer token + 共享根白名单 |
| 安卓端 | 原生 **Kotlin + Jetpack Compose**；**OkHttp** + **kotlinx.serialization**；**Coil 3** 管图片；**无 Rust** |
| 本地持久化（手机） | 配对信息进 EncryptedSharedPreferences / Keystore；待重试队列进 DataStore。**不引 Room** |

### 2.2 依据

**为什么桌面端当主机**（相对 v1 的 WebDAV 直读）：

| | v1 手机直读 WebDAV | **v2 桌面端当主机** |
|---|---|---|
| 手机看一张 RAW 缩略图 | Range 下载 **≤16MB** 再本地解码 | 下载**已缓存好的 300px JPEG**（`thumbnails_v2`），约 30–60KB |
| 一屏 20 张 | ~300MB（4G 不可接受） | ~1MB |
| RAW 格式覆盖 | 只剩"内嵌 JPEG 扫得到"的，**CR3/RAF 有风险** | 与桌面端**完全一致**（四级解码链） |
| 手机端要写的代码 | WebDAV 客户端 + ETag 缓存 + `If-Match` 冲突 + Range + 内嵌 JPEG 扫件 | 一个瘦 HTTP 客户端 |
| 手机端 Rust 核心 | 需要（7 个 FFI 函数 + NDK + UniFFI） | **不需要** |
| 缓存设计 | 自己设计键、版本化、LRU | **Coil/OkHttp 白送**（URL 带 `?v=<mtime>` 即可正确失效） |
| 代价 | — | 电脑必须开着 + ImageFilter 必须运行 + 桌面端多一个安全敏感面 |

**为什么安卓侧是原生 Kotlin**：本项目的首选约束是"动画流程性能优先"，它排除 WebView 方案（WebView 的图像解码链路由 Chromium 代管，App 拿不到 `inSampleSize`、硬件位图、分块解码的控制权）。生态事实：Google Play 检出 Kotlin 约 79%，跨平台里 Flutter 26% / React Native 19%（口径为"被检出的技术栈占比"、可重叠，[来源](https://cloud.tencent.com.cn/developer/article/2615321)）。

**为什么不做中继**：见附录 A #4。这一条直接对齐同类最成熟项目的做法——Immich 的 [Remote Access 文档](https://docs.immich.app/guides/remote-access/) 只给三个选项（VPN 回家 / Tailscale / 反向代理），**它自己一行穿透代码都不写**，并在开头警告"永远不要把端口直接转发到公网"。

## 3. 架构

### 3.1 分层

```
┌──────────────── Android（Kotlin + Compose，无 Rust）────────────────┐
│ ui/    目录树抽屉 · 网格(LazyVerticalGrid) · 滑卡栈 · 查看器        │
│        筛选栏 · 待重试面板 · 配对向导 · 设置                        │
│ data/  ApiClient(OkHttp + Bearer) · DTO(kotlinx.serialization)      │
│        PairingStore(Keystore) · PendingStore(DataStore)             │
│ image/ Coil 3 + 自定义 OkHttp（带鉴权头）+ 磁盘缓存                  │
└───────────────────────────┬────────────────────────────────────────┘
                            │ HTTP + Bearer token
                  局域网 / EasyTier / Tailscale / CF Tunnel（加密隧道）
┌───────────────────────────▼────────────────────────────────────────┐
│ ImageFilter 桌面端（Tauri 2）                                       │
│  【既有】scanner / analyzer / importer / xmp / db / win_wic         │
│  【新增】server/  axum 路由 + 鉴权 + 共享根白名单 + 限流            │
│          mover.rs 移动照片(含边车)                                  │
│          preview_scaled 服务端降采样（给手机合理尺寸）              │
│          app.emit("decisions-changed") → 前端刷新                   │
└────────────────────────────────────────────────────────────────────┘
```

### 3.2 边界纪律（四条）

1. **手机端不解析任何文件格式**。不读边车、不解 RAW、不猜路径规则。
2. **服务层不重写既有逻辑**。缩略图、预览、扫描、边车读写**一律调用既有 command 的实现**，不复制第二份（这个仓库已有"同一套规则在两处写死"的教训，见 `xmp.rs:681` 与 `importer.rs:741` 的对照注释）。
3. **所有路径必须过共享根白名单**。没有例外，包括缩略图。
4. **服务层不许绕过既有的并发限制**。RAW 全解码是 `Semaphore(1)`（交接文档 §4.2），HTTP 层必须限流，否则手机快速滚动会把电脑 CPU 打满——这正是桌面端当年修过的老问题。
   > **实测修正（M0′ Task 4）**：桌面端 `batch_thumbnails` 的 `Semaphore(4)` 是**函数内的局部变量**，HTTP 层根本无法"复用"它。因此服务层建了**两条彼此独立的闸门**：`THUMBNAIL_CONCURRENCY = 4`（**故意等于**桌面端那个数，保证 HTTP 路径永不比用户日常在跑的路径更激进）与 `PREVIEW_CONCURRENCY = 1`（一次 preview 就是全尺寸解码 + Lanczos3 + 重编码，几十到几百 MB；且 RAW 传感器解码已被 `RAW_DECODE_SEM(1)` 串行化，第二个许可几乎买不到吞吐）。**两者不共享许可**，所以两个并发 `full=1` **不会**饿死缩略图请求。**同一客户端的并发限制属于路由层**（需要客户端身份），不在媒体层做。

### 3.3 与桌面端既有机制的关系

| 既有机制 | B′ 下怎么用 |
|---|---|
| 三级解码链 + `thumbnails_v2` / `preview_v4` 缓存 | **直接复用**，手机请求即命中同一份磁盘缓存 |
| `xmp.rs` 的 `read_decisions` / `write_decisions` | **直接复用**。手机端不写边车，写边车的永远是桌面端 |
| `write_decisions` 的"`changed=false` 不写"幂等纪律 | 保留：手机重复提交同一个星级不会白摸一次盘 |
| `useScanner.ts:1020` 打开文件夹时 `read_decisions` | 保留，是"手机改完电脑能看到"的收敛路径 |
| 版本号 4 处（交接文档 §9.2） | 本规格不动版本号；发版时保持一致 |

## 4. 网络层（L0 + L1，不做中继）

### 4.1 L0：App 只认"一个可达 URL + token"

手机侧不假设任何环境。同一 WiFi 下填 `http://192.168.x.x:<port>` 即可用；跨网时那个地址换成隧道分配的虚拟地址。**App 不关心你怎么打通的。**

### 4.2 L1：连接向导内置打通引导 + 自动探测

| 引导项 | 为什么 | 用户要做什么 |
|---|---|---|
| **EasyTier**（首选） | 开源 Apache-2.0、去中心化组网、**不需要账号**、**不需要公网 IP**、有公共共享节点（零服务器成本）、**有安卓 APK 与 Windows GUI**（[官方下载页](http://doc.easytier.cn/guide/download.html)） | 电脑装 GUI 选"公共服务器组网"，手机装 APK 输入同一个网络名/密钥 |
| Tailscale（备选） | 最省心、生态最成熟 | 两端装客户端登录。**注意登录页在境外**，国内可能卡在这一步 |
| Cloudflare Tunnel（备选） | **手机端零安装**、自带 HTTPS | 需要一个域名 + Cloudflare 账号；国内速度一般 |

**自动探测（这是我们可以比 Immich 做得好的地方**——Immich 只给一篇文档）：桌面端检测本机是否已装 EasyTier / Tailscale，若检测到就**把虚拟网地址直接列出来**，用户一键填入配对信息，不必自己去查 `100.x` 或 `10.x` 是多少。

### 4.3 安全边界（必须写死在 UI 上）

- **不提供把服务直接暴露到公网的模式**，也不提供"一键端口转发"。开启服务时若检测到本机有公网可达地址，明确警告。
- **不自己做 TLS**：加密由网络边界提供（局域网，或 EasyTier/Tailscale/WireGuard 这类加密隧道，或 Cloudflare Tunnel 自带的 HTTPS）。理由：自签证书要么训练用户忽略警告，要么引入 TOFU 机制，两条都不划算。
- 明确告知：**同一个不可信 WiFi 下，token 是可被嗅探的**。所以引导里只推荐"局域网 + 加密隧道"两种用法。

## 5. 接口契约

### 5.1 端点

所有端点要求 `Authorization: Bearer <token>`（`/api/v1/ping` 除外，但它在未配对时只返回产品名与版本，不泄露任何路径）。

| 端点 | 复用/新增 | 说明 |
|---|---|---|
| `GET /api/v1/ping` | 新增 | `{ name, version, platform, requiresToken }` —— 配对与"测试连接" |
| `GET /api/v1/shares` | 新增 | 桌面端已配置的**共享根列表**（手机只能在这里面活动） |
| `GET /api/v1/drives` | `detect_drives` | 设备/盘符（可移动优先） |
| `GET /api/v1/browse?path=` | `browse_directory` | **单层**目录（与桌面端同一语义，不做递归） |
| `GET /api/v1/scan?path=` | `scan_directory` | 照片列表（含 EXIF）；服务端按 `SUPPORTED_EXTENSIONS` 过滤 |
| `GET /api/v1/thumb?path=&size=300` | `thumb_single` + `thumbnails_v2` | **返回 JPEG 字节**。`size` 是**闭集 `{150, 300, 600}`**（向下吸附），`size < 150` → `badRequest` |
| `GET /api/v1/preview?path=&max=2048&full=0` | `get_preview_image`（`full=1` 时走 `get_full_image`）+ **新增降采样** | **返回 JPEG 字节**，长边 ≤ `max`；`max` 必须落在 **[64, 5000]**，越界 → `badRequest`（**不再静默钳制**），见 §5.2 画质契约 |
| `GET /api/v1/decisions?paths=…` | `read_decisions` | 读边车（星级/色标） |
| `PUT /api/v1/decisions` | `write_decisions` | 写边车；**写边车的永远是桌面端** |
| `POST /api/v1/move` | **新增**（`mover.rs`） | 移动照片 + 同名边车；返回逐项结果 |
| `GET /api/v1/events` | 新增（SSE，可选） | 桌面端评分变化 → 手机刷新 |
| `GET /api/v1/clients` | 新增（可选） | 已连接来源列表（"谁在连我"） |

### 5.2 关键契约

**鉴权**：token 为 32 字节随机（base64url），生成一次存桌面端 app data dir；UI 可一键轮换（轮换后所有手机需重新配对）。比较用常量时间。

**共享根白名单（安全红线）**：
- 桌面端维护一组共享根（用户在桌面端显式添加，如 `D:\照片`）。
- 每个请求的 `path` 必须 `canonicalize` 后落在某个共享根之下，否则 `403`。**必须防 `..` 逃逸与符号链接逃逸**。
- 缩略图/预览/移动同样受这条约束——没有例外。
- 这条对应桌面端 asset scope 的既有思路：默认全关、按需放行（`allow_asset_dir`，交接文档 §4.6）。
- **实测约束（Task 3）**：`ensure_within` 只能校验**已存在**的路径（必须 `canonicalize` 才能证明包含关系）。因此任何需要校验**待创建路径**的端点，都必须改为**校验其父目录**，否则会被 `NotFound` 挡下。这也是"手机端不支持新建文件夹"这条决定的底层原因之一——服务端没有 `Mkdir`，而即便将来要加，也必须按父目录校验。

**缩略图与预览**：两者都必须被闸门限流，且**各自独立**——缩略图 `THUMBNAIL_CONCURRENCY = 4`、预览/全图 `PREVIEW_CONCURRENCY = 1`（实测修正见 §3.2 第 4 条）。RAW 传感器解码另有既有的 `Semaphore(1)` 在其内层。

*缩略图*：沿用 `thumbnails_v2` 的 `thumb_single`（缓存名 `{hash}_{max_size}.jpg`，键含 mtime）。它优先走 Windows Shell 缩略图，失败才回落解码——**这就是桌面端网格里那张图，手机上不会更差**。默认 `size=300`。**`size` 只接受 `{150, 300, 600}` 这个闭集**（向下吸附，`< 150` 报 `badRequest`）：放开会让每张图最多产生 961 个缓存条目，而 `thumbnails_v2` 目前**没有淘汰机制**。

*预览（画质契约，逐项都有出处）*

| 项 | 约定 | 出处 |
|---|---|---|
| 来源 | 默认 `get_preview_image`（RAW 的内嵌 JPEG / 非 RAW 的原图）；`full=1` 时走 `get_full_image`（WIC/rawler 全解码链） | 交接文档 §4.1 三级解码 |
| 降采样 | **复用 `resize_max_edge`（`FilterType::Lanczos3`）**，与桌面端全图降采样同一套算法 | `images.rs:27` |
| 编码 | **用 `save_jpeg_quality` 显式给质量**（默认 `q=88`）；**不要用 `img.save()`** —— 那走 JPEG 默认质量 ≈75。服务端要编进内存，故编码体已抽成共用的 `encode_jpeg_quality<W: Write>`，**编码参数只允许有一处** | `images.rs`（`save_jpeg_quality` / `encode_jpeg_quality`） |
| 尺寸 | 长边 ≤ `max`（默认 2048），**绝不放大**（`resize_max_edge` 只在超限时缩） | `images.rs:28` |
| 方向 | 返回前必须完成 EXIF 物理校正，**且必须覆盖每一个来源分支**（见下方实测教训） | 交接文档 §5 第 10 条 |
| 缓存 | 落盘，键含 `mtime + max + full` | 见 §9 |

> **方向校正的实测教训（M0′ Task 4；花了两个修复轮才钉住，值得后人少走一遍）**：曾经用"返回路径是否等于请求路径"当代理，判断"这份内容是否已被物理校正过"。**这个假设是错的**：RAW 的最大内嵌 JPEG 在长边 ≥3000 时会被**原样复制**进 `full_v3` 缓存，那些字节**仍带相机 EXIF 方向标签、并未旋转**——于是服务端恰好在该校正时跳过，而编码又不写 EXIF，**手机拿到转了 90° 的图**（同一个文件在桌面端显示正常，因为它的 CSS 用 `image-orientation: from-image`）。
>
> 正确做法是**无条件调用 `apply_exif_orientation`**：文件没有方向标签时它本就 no-op，而编码器写出的缓存**必然没有** EXIF 标签（`image` 的 JPEG 编码器只在显式调用 `set_exif_metadata` 时才写 APP1，本仓库从不调用）。**绝不要再引入"路径相等 ⇒ 已校正"这类代理判断。**

**画质上界必须明示的两条**（UI 文案与文档都要说清楚，不许含糊）：

1. **默认预览的画质上界 = 相机塞进 RAW 的那张内嵌 JPEG 的画质与分辨率**，不是 RAW 的画质。内嵌 JPEG 是相机渲染过的（机内色彩/锐化/降噪/白平衡），与电脑上"全解码 RAW"**不是同一个东西**——不是变差，是不同。桌面端 `FULL_MIN_EDGE = 1500` 这条规则的存在，正说明作者踩过"内嵌预览不够大"的坑；**Sony ARW 尤其要注意**。**已实测（2026-10-07 · `F:\壁纸` 的 8 个真实样张）：ARW 5/5 全部只有 1616×1080；索尼"已增强-降噪"导出的 DNG 更小——1024×683，其中 HDR 那张仅 256×171。8 张里没有一张达到 2048。** 也就是说默认预览在手机上放大到 1:1 验对焦是**不够**的，而这类增强型 DNG **连看构图都勉强**。
2. **广色域（Adobe RGB / Display P3）照片可能偏色**：降采样用的 `image` crate 不处理 ICC。桌面端同样受此限制（属**已知的一致限制**，不是 v2 引入的）。

因此 **`full=1` 对 RAW 是必需项，不是可选优化**（实测：8/8 张的内嵌预览都 < 2048，且 `resize_max_edge` **绝不放大**，所以把 `max` 调大毫无作用）。用户长按图片或点「高清」时按需请求，走**预览专用**闸门（`PREVIEW_CONCURRENCY = 1`），UI 上表现为"加载中"，**绝不阻塞缩略图等其他请求**（缩略图有自己独立的 4 个许可）。

> **`max` 参数对两类来源的意义完全不同，别混为一谈（这是本轮实测暴露出来的一处概念混淆）**：
> - **JPEG 原图**：`get_preview_image` 返回的是**原文件**，源可能有 6000px 宽 —— 此时 `max` 直接决定画质与流量，`标准(2048)` / `高(3072)` 两档**是有意义的**。
> - **RAW**：源就是那张 1616×1080（或更小）的内嵌 JPEG，`max` 写多大都不会更清楚 —— 想更清楚**只能** `full=1`（电脑端全解码，实测样本里有一个 **50.6MB 的线性 DNG**，比解码 ARW 更重）。
>
> 所以设置项给三档没问题，但**绝不要向用户承诺"RAW 选高画质会更清楚"**——那只在 JPEG 上成立。

**关键约束**：服务端降采样**必须复用 `resize_max_edge` 与 `save_jpeg_quality`，不许另写一套重采样/编码**。否则会出现"手机上的预览比电脑上的缩略图还糙"这种找不到原因的观感差异——这个仓库已经有过"同一套规则在两处写死"的教训（`xmp.rs:681` 与 `importer.rs:741`）。

**写决策（`PUT /api/v1/decisions`）**：
- 请求体与桌面端 `DecisionWrite` 同形：`{ path, rating: number|null, label: string|null, clearLabel: boolean }`，`null` 表示"不动这个属性"。
- 复用 `write_decisions`，**原样透出既有的 `WriteSummary`**（`src/types.ts`：`{ written, skipped, failed, failures, degraded }`），**不新造字段**。注意别与 `ImportSummary` 的 `{ imported, skipped, renamed, failed }` 混淆——那是导入归档的口径，本服务不涉及。
- 串行化：同一路径的写请求在服务端排队，避免读-改-写交错（`xmp.rs` 的 `apply_decision` 是读-改-写，`WRITING` 只是进程内闸门）。

**移动（`POST /api/v1/move`）**：
- 请求 `{ paths: [..], destDir: ".." }`；`destDir` 同样受共享根白名单约束。
- 纪律沿用 `importer.rs`：**绝不静默覆盖**（目标已存在 → 报冲突，让用户改名或跳过）。
- **先移照片、再移同名边车**；若边车移动失败，返回"半成功"标记与逐项结果，由手机显示并允许重试。绝不静默吞掉——否则评分会与新路径脱钩。
- **逐项结果恰好五个字段（M0′ Task 7 实测定型）**：`src` / `dest` / `status` / `detail` / **`pendingSidecars`**。
  - `pendingSidecars` 是**机器数据**，类型是**数组**（没有待补项时是 `[]`，**不是 `null`**），每一项是**留在原地的边车源路径**（真实存在，直接过白名单与存在性两关）；**可能多于一项**（两种命名习惯 `{stem}.xmp` / `{name}.xmp` 同时存在时）。
  - **语义不变量**：`status == "halfSuccess"` ⇔ `pendingSidecars` 非空；`moved` / `conflict` / `failed` ⇒ `[]`。
  - **重试通道（手机端必须照此实现，不得推导命名规则）**：`POST /api/v1/move { paths: item.pendingSidecars, destDir: parent(item.dest) }` —— 不需要新端点、不需要新字段、不需要解析 `detail`。`dest` 是照片的规范最终路径，所以它的父目录就是目标目录。
  - **`detail` 是人类可读提示，不是数据通道**（§5.3 的 i18n 纪律：文案在前端本地化）。手机**不得**解析 `detail`。
  - **⚠️ 半成功项的 `src`（照片）已经被移走了**：因为所有源路径都必须 `canonicalize`（只能校验已存在的路径），**任何携带半成功项 `src` 的请求都会整批 404**。所以"全部重试"必须**剔除已不存在的 `src`**，只重发仍待重试的项——这一点有测试钉住。

### 5.3 错误码

沿用这个仓库的**闭集错误码**文化（桌面端已有 `XMP_ERR_CODES`、`LRC_ERR_CODES`）。服务端统一返回 **`{ code }`**，**每条码必须落到"用户下一步做什么"**，文案由手机端按 code 本地化。

> **实测后修正**：原稿写的是 `{ code, detail }`，但实现只发 `code`（`src-tauri/src/server/mod.rs` 的 `IntoResponse` 实测只序列化一个字段）。**方向定在只发 `code`**：把 `detail` 塞进 HTTP 响应等于把中文文案硬编码进 Rust，与既有 i18n 纪律（文案在前端、按 key 本地化）相反。**手机端的 `ApiError` 只消费 `code`** —— 这是**前向要求**，M1′/M2′ 实现时以此为准（写这句话时手机端还没有 `ApiError` 类型）。

**服务端会返回的码**（这张表就是 Rust 侧 `ApiError` 的闭集）：

| code | HTTP | 场景 | 用户动作 |
|---|---|---|---|
| `unauthorized` | 401 | 无/错 token | 重新配对 |
| `forbiddenPath` | 403 | 路径不在共享根内（**只读模式拦下的写操作也复用这个码**） | 提示去电脑上添加共享根 / 电脑上不允许此操作 |
| `notFound` | 404 | 路径不存在 | 刷新目录 |
| `conflict` | 409 | **桌面端写边车时的**目标已存在 / 边车不可写。**注意：`POST /api/v1/move` 的"目标已存在"不走这个码**——它在 HTTP **200** 的逐项结果里报 `status:"conflict"`（批次级 409 会丢掉同一批里成功的那些）。手机端要能区分这两处来源 | 改名 / 跳过 / 看详情 |
| `busy` | 423 | 文件被占用（`xmp.rs` 的 `Busy`）；**也用于"本次请求已被更新的请求取代"**（实测扩充） | 重试 |
| `diskFull` | 507 | `xmp.rs` 的 `DiskFull` | 停止批量并提示 |
| `tooLarge` | 413 | 边车超过 1MB（`XMP_SIZE_LIMIT`） | 不写，提示该边车超限 |
| `notXmp` / `unsupportedForm` | 422 | 边车不是 XMP / 是元素形式；**`unsupportedForm` 也用于"这个构建解不开这张图"**（实测扩充，例如缺 HEIC/AVIF 解码器） | 不写，提示无法安全合并；解不开图时提示"电脑端无法解码此格式"。**两种语义必须给不同文案**（见 M2′ 计划） |
| `badRequest` | 400 | **请求本身不合法**：非绝对路径 / 不支持的扩展名 / 空 stem（`XmpError::Unknown` 也映射到这里）；**以及 `thumb` 的 `size` 越界与 `preview` 的 `max` 越界**（实测扩充） | 换一个请求——**不要改名后拿同一个坏路径重试** |
| `internal` | 500 | 未预期错误 | 报 bug |

**手机端合成的状态**（**服务端永远不会返回这些**——"服务没开"时根本没有进程在监听，不可能有 HTTP 响应）：

| code | 场景 | 用户动作 |
|---|---|---|
| `timeout` / `network` | 隧道断、电脑睡了、请求超时 | 进待重试 |
| `serviceOff` | 连不上服务（由手机端在连接失败时合成） | 提示去电脑上开启 |

> **为什么必须把这两类分开**：照着混在一起的表实现，客户端会去处理**永远收不到**的码，却漏掉**真会收到**的 `badRequest`/`internal`（Task 3 独立评审发现）。

**三条纪律**：① 绝不静默覆盖；② 半成功态显式化（逐项结果 + 可重试）；③ **"未同步 ≠ 已同步"**——任何"手机上改了但电脑上没写成"的状态都必须在 UI 上可见。

> **已知取舍（Task 3 评审提出）**：`403 forbiddenPath`（存在但在共享根外）与 `404 notFound`（不存在）的区分构成一个**存在性预言机**——已配对的客户端可以探测任意共享根之外的路径是否存在。它**不构成读越权**（读取仍被白名单拦住），而且 `404` 对"照片被删了"这种情形是有用信息，因此**接受这个取舍**。若要关掉它：先 `canonicalize` 父目录，只有在父目录落在共享根内时才允许返回 404，否则一律 `forbiddenPath`。

> **接口细节（Task 6 评审提出，手机端必须知道，否则一定写错）**：`PUT /api/v1/decisions` **成功时**返回 `200 + WriteSummary`，其中**逐项失败的码用的是 XMP 的码集**（`XMP_ERR_CODES`：`readOnly` / `writeProtect` / `permission` / `encoding` / `pathTooLong` / `notXmp` / `tooLarge` / `busy` / `diskFull` / `unknown`），**不是** §5.3 那个 HTTP 的 `{code}` 闭集。
>
> **手机端必须准备两张不同的本地化表**：HTTP 错误体的 `code` 查 §5.3 的表；`WriteSummary.failures[].code` 查 XMP 表。**绝不要混成一张**——两张表的交集只有 `notXmp` / `tooLarge` / `busy` / `diskFull` 四个，`readOnly` / `permission` / `encoding` / `pathTooLong` 在 HTTP 表里根本不存在。

## 7. 手机端结构

| 模块 | 内容 |
|---|---|
| `net/` | `ApiClient`（OkHttp，带 Bearer 拦截器、超时、重试）、DTO、错误码映射 |
| `data/` | `PairingStore`（Keystore / EncryptedSharedPreferences）、`PendingStore`（DataStore，待重试的决策）、内存中的当前文件夹列表 |
| `image/` | Coil 3 `ImageLoader`：OkHttp 实例**带鉴权拦断器**；磁盘缓存；`?v=<mtime>` 做失效 |
| `ui/` | 目录树抽屉 · 网格 · 滑卡栈 · 查看器 · 筛选栏 · 配对向导 · 设置 · 待重试 |

**为什么不引 Room**：B′ 下本地状态极少（配对信息、待重试项、当前文件夹的元数据）。照片列表每次从服务端拉即可——都是元数据，很快。**不引 Room 就省掉一套 schema/迁移**。

**查看器缩放**：预览已被服务端降到 ≤2048px，所以**用 Compose 的 `transformable` + `graphicsLayer` 自绘缩放即可**，不需要引入 `SubsamplingScaleImageView`（那是为超大图分块解码准备的，这里用不上）。这比 v1 的方案简单。

**待重试队列**：写失败的决策进 `PendingStore`，顶栏角标显示数量，可单项/全部重试。**它很小**——不是 v1 那种"离线优先的冲突合并"，只是"请求失败留个痕"。因为写边车的永远是桌面端，不存在两个写入者互相覆盖的问题。

## 8. 交互与信息架构

底部三 Tab：**浏览** / **筛片** / **设置**（待重试项以角标形式挂在浏览页顶栏，不再单独占一个 Tab——B′ 下它的内容量远小于 v1）。

### 8.1 浏览
- 左侧抽屉：共享根 + 目录树
- 主区：`LazyVerticalGrid` 缩略图网格，列数可配 2–6（对应桌面端 `-cols`）
- 顶栏：当前文件夹名 / 张数 / 筛选条件摘要 / 待重试角标
- 筛选栏：**只有星级、色标、待重试三个维度**（分析标记维度不存在，因为不做 AI）

### 8.2 筛片（滑卡）
- 卡片栈：当前张 + 后 2 张预取（预取的是 **2048px 预览**，由服务端给，约 300–600KB/张）
- 底部：1–5 星、色标面板、撤销（多步，内存栈上限 50）
- **默认映射对齐桌面端 `J`/`X`**（README 快捷键表：`J` = 保留（3 星）、`X` = 废弃（0 星）），共用同一个 `xmp:Rating` 字段：

| 手势 | 默认写入 | 规则 |
|---|---|---|
| 左滑（废弃） | `rating = 0` | 直接写 |
| 右滑（保留） | `rating = 3` | **仅当当前无星级（空或 0）时才写 3**；已有 ≥1 星则**不改星级**，只提示"已保留 · 保持 N★" |

第二行那条限制是必须的：无条件写 3 会把桌面端已给的 4/5 星**静默降级**。命中"不降级"那一支时**不产生写入**，但**仍自动前进**并给出明确反馈。

可配置（设置项「滑卡写入」）：`只写星级`（默认）/ `只写色标`（左红右绿）/ `星级 + 色标都写`。

- **手势规则写死**：默认态单指拖动 = 滑卡决策；**双指缩放进入查看态**（单指 = 平移，滑卡禁用）；双指缩回恢复决策态；长按 = 色标面板。不定死的话，缩放与滑卡一定会互相抢手势。
- 写成功才自动前进；失败则留在原张并标待重试（避免"以为打过了"）。

### 8.3 配对
扫码（桌面端设置页显示二维码，内容为 `{url, token}`）或手输。配对后立即验证 `/ping` 与 `/shares`，失败就给四条排查提示（§1.3）。

## 9. 缓存与离线

| 层 | 内容 | 归属 |
|---|---|---|
| 桌面端缩略图缓存 | 300px，`thumbnails_v2`，键含 mtime | **已存在**，复用 |
| 桌面端预览缓存 | 手机请求的降采样结果，键含 `mtime + max + full` | 新增（否则每次请求都要解码 + Lanczos3，CPU 白烧） |
| 手机端图片缓存 | Coil 内存 + 磁盘缓存（OkHttp），键 = URL（含 `?v=<mtime>`） | 新增，但**由 Coil 提供** |
| 手机端待重试 | 写失败的决策 | DataStore，量很小 |

**离线边界**：离线时网格显示 Coil 已缓存的缩略图、查看器显示已缓存的预览；**打分/色标/滑卡/移动全部失败并进待重试**，顶部横幅说明原因。这份状态必须显式显示，不能让用户打完分才发现白打。

**缓存失效**：URL 带 `?v=<mtime>`，桌面端的 `scan_directory` 已返回 `modifiedAt`。文件被移动后路径变、URL 变，会重新拉——但服务端有 `thumbnails_v2` 命中，成本只是一次网络往返。**这个取舍可接受**（v1 用 ETag 是为了避免重下 16MB RAW，B′ 下缩略图只有几十 KB，不值得为它设计内容寻址）。

### 10.1 模拟器能验什么、不能验什么

| | 模拟器 | 真机 |
|---|---|---|
| 功能正确性（配对/列目录/缩略图/打分/移动/错误码分支/布局溢出） | ✅ 可信 | ✅ |
| 离线与待重试行为 | ✅ 可信 | ✅ |
| **滑卡跟手度、缩放内存、大图换页** | ❌ 帧率与触摸采样都不是真的 | ✅ 唯一可信 |
| **性能预算（120Hz 掉不掉帧）** | ❌ 宿主 GPU/CPU 与手机差太远 | ✅ |

**必须真机的清单**：① 滑卡跟手度与回弹；② 双指缩放与查看态切换是否打架；③ 连续翻 100 张的内存曲线；④ 大图换页是否闪黑；⑤ 弱网/断网切换时的横幅与入口禁用。

## 11. 风险与缓解

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **电脑睡眠 → 远程全断**，且用户从手机侧看不出原因 | 服务面板给出"电源与睡眠"检查项与设置指引；契约脚本能在电脑本机区分"服务没起"与"网络不通" |
| 2 | **服务是新的安全敏感面**（它能让持有 token 的人读你指定的目录） | 默认关闭、强制 token、常量时间比较、**共享根白名单**、不做 TLS 但明确禁止公网暴露、已连接来源可见、token 可轮换 |
| 3 | **共享根白名单写不严 → 目录穿越** | 用 `canonicalize` + 前缀比对，单测必须覆盖 `..` 与符号链接两种逃逸；缩略图/预览/移动三条路径都要测 |
| 4 | **手机快速滚动把电脑 CPU 打满**（桌面端当年修过的老问题） | HTTP 层设**两条独立闸门**（缩略图 4、预览/全图 1，见 §3.2 第 4 条）+ 既有的 RAW `Semaphore(1)`；**同一客户端的并发限制待路由层实现（M0′ Task 8）** |
| 5 | 服务端**预览降采样**是新增的 CPU 活（每次请求都要解码+重采样） | 降采样结果落盘缓存（键含 mtime + max），命中后是纯 IO |
| 6 | **本机不能验证 UI** → "写完不知道对不对" | M0′ 全部留在可单测范围；§10.1 真机清单写死；模拟器只当功能验证 |
| 7 | **模拟器不可作为性能验收依据** | 性能结论只来自真机 + `screenrecord` 掉帧统计 |
| 8 | **EasyTier 相对小众**，公共节点速度不保证 | 引导里三个选项平级列出（只是排序不同），并给出各自官网；文档说明速度取决于公共节点与是否自建 |
| 9 | 桌面端前端也要改（服务面板），与"少动前端"的纪律冲突 | 改动**限于 `settings-dialog.tsx` 与 `useScanner.ts` 各一处**；禁止动 `App.tsx` 布局 |

## 12. Token 纪律（为后续会话省成本）

AI 协作下，**token 成本 ≈ 需要人读的代码量 + 需要设备验证的循环次数**。

1. **单文件 ≲ 300 行**。超了就拆（`server/` 按职责分 `mod/auth/routes/dto` 四个文件就是为了这个）。
2. **可单测面积最大化**。鉴权、白名单、错误码映射、移动纪律全部放 Rust 单测；手机端数据层放 JVM 单测。**跑测试的输出是短的，跑模拟器截图 + logcat 的输出是贵的**。
3. **桌面端改动限于 §6 列出的 11 个文件**。禁止顺手重构 `App.tsx`（48KB）/ `useScanner.ts`（65KB）/ `index.css`（19KB）/ `viewer.tsx`（30KB）。
4. **禁止在实施会话里读大文档全文**：`ImageFilter-功能实施方案.md`（167KB）与 `ImageFilter-架构与机制走查.md`（50KB）只按需 grep 小节；本规格 + 交接文档 §0/§4/§5 足够。
5. **i18n 双文件必须齐**（zh/en），改完跑 `docs/evidence/scripts/i18n-parity.cjs`。
6. **手机端不引 Room**、不引 `SubsamplingScaleImageView`——每一项都是要读代码的负担。
7. **一个里程碑一个会话**。
8. **脚本按 PowerShell 7 写，并用「自举」而不是 `#Requires`**。实测结论（见附录 B #12）：本 harness 的 shell **写死**为 `C:\WINDOWS\System32\WindowsPowerShell\v1.0\powershell.exe`，装了 PS7 并写入用户 PATH 之后**当前会话依然不变**（父进程环境陈旧，`$env:Path` 里根本没有新目录）。所以 `#Requires -Version 7` 会让脚本在 5.1 下**直接失败**——改为脚本开头检测版本并**自己切到 PS7 再跑**（`-File` 通路已实测可用，脚本内引号不会丢）。另有一条同样实测出来的坑：**从 harness 内联调用 PS7 时，`-Command` 的引号会被多一层解析吃掉**（内层双引号被剥掉导致语法错误），跑内联代码要用 `-EncodedCommand`（base64 / UTF-16LE，完全免疫引号层）。
  同源的第三条陷阱：**PS 5.1 对没有 BOM 的文件一律按 ANSI(GBK) 解码**。后果有两面——① `.ps1` 里的中文注释会让**解析错位**（实测报出与实际行号不符的语法错误），所以脚本必须存成 **UTF-8 带 BOM**；② `Get-Content` 会把无 BOM 的 UTF-8 文件**显示成 mojibake**，而文件内容其实是好的（**别被显示骗了，用 `[System.IO.File]::ReadAllText` 或 `Get-Content -Encoding UTF8` 复核**）。
9. **证据输出要短**：验证命令只回传断言结果与关键数字，不要 dump 整页 UI 树 / 完整 JSON。
10. **跑 `cargo` 一律加 `--manifest-path src-tauri/Cargo.toml`**，不要依赖当前目录。实测坑：PowerShell 的 `cd` **会**改变子进程的工作目录，而工具层另有 `workdir` 参数——两者混用会让 cargo 跑到仓库根、报 `could not find Cargo.toml`，而且看起来像"测试跑完没输出"（Task 2 因此白跑一次）。同源的第二点：`[System.IO.File]::ReadAllText` 的相对路径也按**进程 CWD** 解析，不是 PS 的当前位置。

## 13. 交付与发布

- CI：现有 Windows/macOS 构建保持不变；新增一个 Android job（JDK 17 + Android SDK，**不需要 NDK**——B′ 下手机端没有 Rust）产出 APK 作为 Release asset。
